The Rust Programming Language

RefCell<T>与内部可变性模式

“内部可变性”是Rust中的一种设计模式，它允许你在存在不可变引用的情况下修改数据。通常情况下，这种操作是被借用规则所禁止的。为了实现数据修改，该模式会在数据结构内部使用unsafe代码，从而打破Rust中关于变异和借用的一般规则。使用Unsafe代码可以向编译器表明，我们是手动检查这些规则，而不是依赖编译器来为我们进行检查。我们将在第20章中更详细地讨论不安全的代码。

我们只能在能够确保借用规则在运行时得到遵守的情况下，使用采用内部可变性模式的类型。尽管编译器无法保证这一点，但涉及的unsafe代码会被封装在一个安全的API中，而外部类型仍然保持不可变性。

让我们通过查看遵循内部可变性模式的RefCell<T>类型来探讨这个概念。

在运行时强制执行借用规则

与Rc<T>不同，RefCell<T>类型代表了对数据的单一所有权。那么，是什么让RefCell<T>与Box<T>这样的类型有所不同呢？请回想一下你在第4章中学到的借用规则：

  • 在任何时候，你可以拥有一个可变引用，或者任意数量的不变引用（但不能同时拥有两者）。
  • 引用必须始终有效。

通过引用和Box<T>，借用规则的不变量在编译时就被强制执行了。而通过RefCell<T>，这些不变量则在运行时被强制执行。使用引用方式时，如果你违反了这些规则，将会出现编译器错误。而使用RefCell<T>时，如果你违反了这些规则，程序将会崩溃并退出。

在编译时检查借用规则的优势在于，可以在开发过程中更早地发现错误，而且由于所有分析都在事先完成，因此不会影响到运行时的性能。基于这些原因，在大多数情况下，编译时检查借用规则是最佳选择，这也是Rust的默认行为。

在运行时检查借用规则的优势在于，某些内存安全的场景可以被允许，而这些场景在编译时检查中是不被允许的。静态分析，比如Rust编译器，本质上是一种保守的方法。有些代码特性是无法通过分析代码来检测的：最著名的例子就是停机问题，这个问题超出了本书的讨论范围，但确实是一个值得研究的话题。

因为有些分析是不可能的，如果Rust编译器无法确定代码是否符合所有权规则，它可能会拒绝一个正确的程序。这样一来，Rust的做法就显得比较保守。如果Rust接受一个错误的程序，用户就无法相信Rust所做出的保证。然而，如果Rust拒绝一个正确的程序，程序员会感到不便，但并不会发生什么灾难性的情况。当您确信RefCell<T>类型时，它非常有用。代码遵循了借用规则，但编译器无法理解和保证这一点。

类似于“Rc”，“RefCell”仅适用于单线程场景，如果你尝试在多线程环境中使用，会给你编译时错误。我们将在第 16 章讨论如何在多线程程序中实现“RefCell”的功能。

以下是选择Box<T>、Rc<T>或RefCell<T>的理由总结：

  • Rc<T>支持同一数据由多个所有者管理；Box<T>和RefCell<T>则只有单个所有者。
  • Box<T>允许在编译时检查可变或不可变的借用行为；Rc<T>仅允许在编译时检查不可变的借用行为；RefCell<T>允许在运行时检查可变或不可变的借用行为。
  • 因为“RefCell”允许在运行时检查可变借用，即使 “RefCell”是不可变的，也可以在“RefCell”内部变异。

在不可变值内部修改其值是内部可变性模式。让我们来看一个内部可变性有用的场景，并探讨如何实现这种特性。

使用内部可变性

借用规则的一个结果是，当你有一个不可变的值时，你不能对其进行可变借用。例如，这段代码将无法编译：

fn main() {
    let x = 5;
    let y = &mut x;
}

如果你尝试编译这段代码，将会出现以下错误：

然而，在某些情况下，让一个值在自身的方法中发生变异，但对其他代码来说却看起来是不可变的，这是非常有用的。位于该值方法之外的代码将无法对该值进行变异。使用RefCell<T>是一种实现内部可变异性的方法，但RefCell<T>并不能完全解决借用问题：编译器的借用检查器允许这种内部可变性，而借用规则仍然需要被检查。改为在运行时进行。如果你违反了规则，你将收到一个panic!的提示，而不是编译器错误。

使用模拟对象进行测试

在测试过程中，有时程序员会使用一种类型来代替另一种类型，以便观察特定的行为，并确认该类型是否正确实现。这种占位符类型被称为“测试用双精度型”。可以将其想象成电影中的替身演员，他们代替真实的演员来表演特别复杂的场景。当我们进行测试时，测试用双精度型就代表了其他类型。而“模拟对象”则是特定类型的测试工具。该记录详细描述了测试过程中的所有事件，以便您可以确认正确的操作确实已经执行了。

Rust中的对象与其他语言中的对象有所不同，而且Rust的标准库中没有内置类似于其他语言中的模拟对象功能。不过，您完全可以创建一个结构体，使其具备与模拟对象相同的功能。

运行时跟踪借用情况

在创建不可变和可变引用时，我们分别使用&和&mut语法。对于RefCell<T>，我们使用borrow和borrow_mut方法，这些方法属于安全API的一部分，而该安全API又归属于RefCell<T>。borrow方法返回智能指针类型Ref<T>，而borrow_mut则返回智能指针类型RefMut<T>。这两种类型都实现了Deref功能，因此……可以像对待普通的引用一样处理它们。

RefCell<T> 记录了当前有多少个 Ref<T> 和 RefMut<T> 智能指针处于活动状态。每次调用 borrow 时，RefCell<T> 会增加其不可变借用对象的数量。当 Ref<T> 的值超出作用域时，不可变借用的数量就会减少1。就像编译时的借用规则一样，RefCell<T> 允许我们在任何时候拥有多个不可变借用对象，或者只有一个可变借用对象。

如果我们试图违反这些规则，那么编译器不会报错，而是会在运行时导致RefCell<T>的实现出现异常。清单15-23展示了对清单15-22中send实现的修改。我们故意尝试创建两个可变的借用关系，它们作用于同一个作用域，以此来说明RefCell<T>能够在运行时阻止我们这样做。

我们为从borrow_mut返回的RefMut<T>智能指针创建了一个变量one_borrow。然后，我们以相同的方式在变量two_borrow中创建了另一个可变的借用对象。这样就在同一个作用域中创建了两个可变引用，这是不允许的。当我们运行库中的测试时，Listing 15-23中的代码会成功编译，但测试将会失败：

选择在运行时而不是编译时捕获借用错误，就像我们在这里所做的那样，意味着你在开发过程中可能会发现代码中的错误——可能要等到代码被部署到生产环境之后才会被发现。此外，由于需要在运行时而不是编译时跟踪借用情况，代码的运行性能会略有下降。不过，使用RefCell<T>可以编写一个模拟对象，从而……它会自我修改，以记录你在使用它时所看到的消息。在这种情况下，只允许使用不可变的值。尽管存在这些限制，你仍然可以使用RefCell<T>来获得比常规引用更多的功能。

允许多个可变数据的所有者

使用RefCell<T>的一种常见方式是与Rc<T>结合使用。需要注意的是，Rc<T>允许某些数据拥有多个所有者，但它仅提供对该数据的不可修改的访问权限。如果你有一个Rc<T>，其中包含了RefCell<T>，那么你可以获取一个具有多个所有者且可以被修改的值！
