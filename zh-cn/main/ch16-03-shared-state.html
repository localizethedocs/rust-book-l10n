The Rust Programming Language

共享状态并发

消息传递是一种很好的方式来处理同币种，但不是唯一的方式。 另一种方法是多个线程访问相同的共享数据。 再次考虑Go 语言文档的这一部分口号：“不要分享内存。”

分享记忆会有什么样子来沟通？此外，为什么信息传递爱好者会告诫不要使用内存共享？

从某种意义上讲，任何编程语言中的频道都类似于单个所有权，因为一旦您转移了一个通道的值。 您不应再使用该值。 共享内存同义类似于多个所有者：多个线程可以同时访问相同的内存位置。 正如你在第15章中所看到的那样，智能指针使得多个所有权成为可能，多个所有权可以增加复杂性，因为这些不同的所有者需要管理。 俄罗斯的类型系统和所有权规则极大地有助于使管理正确无误。 例如，让我们看一下mutexes，一个更常见的内存首字母。

使用互斥锁控制访问

_Mutex_是_互斥_的缩写，意味着在任何给定时间，只有一个线程可以访问某些数据。要访问mutex中的数据，线程必须先通过请求获取mutex的锁来表明它希望访问这些数据。_锁_是一种数据结构，它是mutex的一部分，用于记录当前谁拥有对数据的独占访问权。因此，mutex通过锁定系统来“保护”其所持有的数据。

由于您必须记住两条规则，因此Musexes 因难以使用而信誉积分：

  1. 您必须先尝试获取锁定才能使用数据。
  2. 当你使用mutex护卫的数据完成时，你必须解锁数据，以便其他线程能够获取锁定。

为了更好地理解互斥锁的工作原理，我们可以想象一个会议上的小组讨论场景。在这个场景中，只有一个麦克风可供使用。在一位小组成员发言之前，他们必须先请求或示意其他小组成员可以使用麦克风。当他们拿到麦克风后，就可以随心所欲地发言，然后将其交给下一位想要发言的小组成员。如果某位小组成员在发言结束后忘记将麦克风交还，那么其他成员就无法发言了。如果共享麦克风的管理不当，整个讨论就会无法按计划进行！

互斥体的管理非常难以掌握，这就是为什么很多人对通道感到兴奋。不过，得益于Rust的类型系统和所有权规则，锁定与解锁的操作根本不会出错。

Mutex<T> 的 API

作为使用互斥锁的一个示例，我们先来看一下在单线程环境中如何使用互斥锁，如清单 16-12 所示。

和许多类型一样，我们使用相关函数new创建一个 Mutex<T>。 为了访问mutex内部的数据，我们使用 lock 方法获取锁定。 此通话将阻止当前的线程，以便在我们转向锁定之前它无法完成任何工作。

如果持有锁定的另一个线程出现恐慌，调用lock将失败。 在这种情况下，任何人都无法得到锁定， 所以，如果我们处于这种局面，我们选择`解除包裹’并有这个线程恐慌。

当我们获得锁定后，我们可以将这个名为num的退货值作为可变的内在数据引用。 类型系统确保我们在使用“m“中的值之前获得一个锁。 m的类型是 Mutex<i32>，而不是 i32，所以我们必须调用lock 才能使用 i32 值。 我们不能忘记；这种类型的系统不会让我们以其他方式访问内部的 i32。

调用lock返回一个叫MutexGuard的类型，包装在一个 LockResult 中，我们用调用unwrawra来电来处理这个类型。 MutexGuard型号实现Deref，指向我们的内部数据； 类型还有一个 Drop 实现，在一个 MutexGuard 超出范围时自动释放锁， 内部范围末尾发生这种情况。 结果， 我们不会忘记解锁锁并阻止mutex 被其他线程使用，因为锁定会自动释放。

在释放锁之后，我们可以打印出互斥量的值，从而看到我们成功地将内部的 i32 改为了 6。

比较Refcell<T>/Rc<T> 和 Mutex<T>/Arc<T>

你可能已经注意到“计数器“是不可变的，但我们可以获得一个可变的内在值的参考值； 这意味着Mutex<T>提供内部可变性，就像Cell家族所做的那样。 同样，我们在第15章中使用了 Refcell<T>，允许我们在一个 Rc<T>中变换内容， 我们使用 Mutex<T>来变换Arc<T> 中的内容。

另一个要注意的细节是，当你使用 Mutex<T>时，Rust 无法保护你免受各种逻辑错误的伤害。 回顾第15章中使用Rc有创建参考周期的危险， 其中两个Rc值相互交错，造成内存泄漏。 同样，Mutex可能会造成_learlocks_。 这种情况发生在一个操作需要锁定两个资源和两个线程各获得一个锁的时候， 使他们永远等待对方。 如果您对僵局感兴趣，请尝试创建一个陷入僵局的灰尘程序； 然后研究以任何语言为母语采取的缓解僵局战略，并在俄罗斯执行这些战略。 Mutex和MutexGuard`的标准库 API 文档提供了有用的信息。
