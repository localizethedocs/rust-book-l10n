The Rust Programming Language

match控制流结构

Rust 拥有一个非常强大的控制流结构，称为 match。它允许你将一个值与一系列模式进行比较，然后根据匹配到的模式来执行相应的代码。这些模式可以包含字面值、变量名、通配符等多种元素；第19章 详细介绍了各种模式及其功能。 match 的强大之处在于其模式的表达能力，以及编译器能够确保所有可能的情况都被处理。

可以将 match 表达式想象成一个硬币分类机：硬币沿着一条带有不同大小孔洞的轨道下滑，每枚硬币会掉入第一个符合其尺寸的孔洞中。同样地，值也会通过 match 中的每个模式，当值符合某个模式时，它就会落入相应的代码块中，并在执行时被使用。

说到硬币，我们就以 match! 为例来演示一下。我们可以编写一个函数，该函数接收一个未知的美国硬币，然后像计数机一样，确定硬币的种类，并返回其价值，以美分为单位，如清单 6-3 所示。

让我们来分析一下 value_in_cents 函数中的 match 部分。首先，我们看到的是 match 这个关键字，后面跟着一个表达式，在这个例子中，这个表达式就是值 coin。这看起来很类似于与 if 一起使用的条件表达式，但实际上有很大的区别：在 if 中，条件需要被评估为一个布尔值，而在这里，条件可以是任何类型。在这个例子中， coin 的类型就是我们在第一行定义的 Coin 枚举类型。

接下来是 match 这个分支。一个分支包含两部分：一个模式和一些代码。这里的第一个分支有一个模式，即值 Coin::Penny，然后是一个 => 运算符，用于分隔模式和要执行的代码。在这种情况下，代码就是值 1。每个分支通过逗号与下一个分支分隔开来。

当 match 表达式执行时，它会依次将结果值与每个分支的模式进行比较。如果某个模式与值匹配，那么与该模式相关的代码就会被执行。如果某个模式与值不匹配，那么执行将继续到下一个分支，就像在硬币分类机中一样。我们可以根据需要设置任意多个分支：在 Listing 6-3 中，我们的 match 有四个分支。

与每个分支相关的代码都是一个表达式，而在匹配分支中该表达式的结果值，就是整个 match 表达式所返回的值。

如果匹配分支的代码较短，我们通常不会使用花括号。正如清单6-3所示，每个分支仅返回一个值。如果你想在匹配分支中运行多行代码，就必须使用花括号，而分支后面的逗号则不是必需的。例如，以下代码在每次方法被调用时都会打印“Lucky penny!”，但它仍然会返回该代码块中的最后一个值：1。

enum Coin {
    Penny,
    Nickel,
    Dime,
    Quarter,
}

fn value_in_cents(coin: Coin) -> u8 {
    match coin {
        Coin::Penny => {
            println!("Lucky penny!");
            1
        }
        Coin::Nickel => 5,
        Coin::Dime => 10,
        Coin::Quarter => 25,
    }
}

fn main() {}

绑定到值的模式

Match Arms的另一个有用特性是，它们可以绑定到与模式匹配的值部分。通过这种方式，我们可以从枚举变体中提取出相应的值。

例如，让我们修改其中一个枚举变体，以在其内部存储数据。从1999年到2008年，美国为50个州各自铸造了不同设计的25美分硬币。没有其他硬币具有州特定的设计，因此只有25美分硬币具有这种额外价值。我们可以通过修改 Quarter 变体来添加这些信息，使其内部存储一个 UsState 值，正如我们在清单6-4中所做的那样。

让我们想象一个朋友正在尝试收集全部50个州造币券。当我们按照硬币类型整理零钱时，我们还会说出每个硬币所代表的州名，这样如果朋友没有这种硬币，他们就可以把它添加到他们的收藏中。

在这段代码的匹配表达式中，我们在匹配 variant Coin::Quarter 值的模式中添加了一个名为 state 的变量。当匹配到 Coin::Quarter 时， state 变量将绑定到该季度的状态值。然后，我们可以在相应分支的代码中使用 state，如下所示：

#[derive(Debug)]
enum UsState {
    Alabama,
    Alaska,
    // --snip--
——剪——
}

enum Coin {
    Penny,
    Nickel,
    Dime,
    Quarter(UsState),
}

fn value_in_cents(coin: Coin) -> u8 {
    match coin {
        Coin::Penny => 1,
        Coin::Nickel => 5,
        Coin::Dime => 10,
        Coin::Quarter(state) => {
            println!(状态季度来自 {state:?}!);
            25
        }
    }
}

fn main() {
    value_in_cents(Coin::Quarter(UsState::Alaska));
}

如果我们称 value_in_cents(Coin::Quarter(UsState::Alaska)) 为 coin，那么 coin 就相当于 Coin::Quarter(UsState::Alaska)。当我们比较这个值与各个匹配项时，直到遇到 Coin::Quarter(state) 之前，都没有匹配项能够匹配上。在到达 Coin::Quarter(state) 时， state 的绑定值就会变成 UsState::Alaska。然后我们可以在 println! 表达式中利用这个绑定值，从而获取 Quarter 中 Coin 枚举变体所对应的内部状态值。

Option<T> match 模式

在上一节中，我们试图从使用 Option<T> 的 Some 情况中提取出 T 的值。同样地，我们也可以使用 match 来处理 Option<T>，就像我们对 Coin 枚举所做的那样！与其比较硬币，我们不如比较 Option<T> 的各种变体，不过 match 表达式的运作方式保持不变。

假设我们想要编写一个函数，该函数接受一个 Option<i32> 参数。如果参数内部有值，则将该值加1。如果参数内部没有值，那么该函数应该返回 None 的值，并且不尝试执行任何操作。

这个函数非常容易编写，多亏了 match，它的样子就像清单6-5所示。

让我们更详细地检查第一次执行 plus_one 的情况。 当我们调用 plus_one(fiv) 时，plus_one 中的变量x将具有有意义(5) 的值。然后我们比较这个变量与每个匹配的装甲：

fn main() {
    fn plus_one(x: Option<i32>) -> Option<i32> {
        match x {
            None => None,
            Some(i) => Some(i + 1),
        }
    }

    let five = Some(5);
    let six = plus_one(five);
    let none = plus_one(None);
}

有些(5)不匹配模式None，所以我们继续到下一个手臂：

fn main() {
    fn plus_one(x: Option<i32>) -> Option<i32> {
        match x {
            None => None,
            Some(i) => Some(i + 1),
        }
    }

    let five = Some(5);
    let six = plus_one(five);
    let none = plus_one(None);
}

有些(5)匹配某些(i)吗？它！我们有相同的变量。 i绑定到有意义'中的值，所以i将获得5的值。 然后执行比赛臂中的代码， 所以我们在 i 中添加了 1 个值，并且创建了一个新的 有意义的值，我们的总值为 6` 。

现在我们来看看名单6-5中的plus_one的第二次通话，x为无'。我们输入匹配`并比对第一个手臂：

fn main() {
    fn plus_one(x: Option<i32>) -> Option<i32> {
        match x {
            None => None,
            Some(i) => Some(i + 1),
        }
    }

    let five = Some(5);
    let six = plus_one(five);
    let none = plus_one(None);
}

它匹配！没有要添加的值，因此程序停止并返回=>右侧的`无’。 由于第一支手臂匹配，没有其他武器进行比较。

合并匹配和enums在许多情况下是有用的。 你会看到这个图案在Rust代码中很多: “匹配” 与一个枚举, 将变量绑定到数据内，然后执行基于它的代码。 最初，它有点棘手，但是一旦你被用了，你就会希望你能够用所有的语言做到。 这是一个收藏的用户。

比赛是完全的

我们需要讨论的 match 的另一个方面：武器模式必须包含所有的可能性。 请考虑这个版本的我们的 plus_one 函数，这个函数有一个错误，将不会编译：

fn main() {
    fn plus_one(x: Option<i32>) -> Option<i32> {
        match x {
            Some(i) => Some(i + 1),
        }
    }

    let five = Some(5);
    let six = plus_one(five);
    let none = plus_one(None);
}

我们没有处理 None 案件，所以这个代码会导致错误。 幸运的是，它是一个Bug Rust 知道如何捕获。如果我们尝试编译这个代码，我们会收到这个错误：

你知道我们没有涵盖所有可能的情况，甚至知道我们忘记了哪种模式！ Rust 中的比赛是 expave: 我们必须用尽所有最后的可能性才能使代码有效。 特别是在 Option<T>的情况下，当Rust 阻止我们忘记明确处理None案例时， 它保护我们不要假定当我们可能有空时我们有价值，从而使早些时候讨论的数十亿美元的错误变得不可能。

全面捕捉模式和 _ 占位符

使用枚举，我们也可以对几个特定值采取特别行动，但对所有其他值则采取一种默认行动。 想象一下我们正在执行一场游戏，如果你在一张冰卷上滚动3的话， 你的玩家没有移动，而是得到了一个漂亮的新帽子。 如果你滚动7个，你的玩家就会失去一个漂亮的帽子。 对于所有其他值，您的玩家移动游戏板上的空格数。 这是一个 match ，它实现了那个逻辑，其结果是舞蹈卷硬编码而不是随机的值。 和所有其他由没有机构的职能所代表的逻辑，因为实际执行它们是超出范围的，例如：

fn main() {
    let dice_roll = 9;
    match dice_roll {
        3 => add_fancy_hat(),
        7 => remove_fancy_hat(),
        other => move_player(other),
    }

    fn add_fancy_hat() {}
    fn remove_fancy_hat() {}
    fn move_player(num_spaces: u8) {}
}

对于头两种武器，它们的模式是字母3和7。 对于覆盖所有其他可能值的最后一个手臂，模式是我们选择命名为“其他”的变量。 运行 other 臂的代码使用变量，将它传递到 move_player 函数。

这个代码编译，即使我们还没有列出一个 u8 可能具有的所有值。 因为最后一个模式将匹配未具体列出的所有值。 这种包罗万象的模式满足了`匹配’必须详尽无遗的要求。 请注意，我们必须把包罗万象的武器放在最后，因为对模式的评价是正确的。 如果我们早些时候放下了包罗万象的武器，其他武器将永远不会运转。 这样，如果我们在抓获后添加武器，Rust 将会警告我们！

Rust 还有一个模式，当我们想要捕捉所有但不想_use_the value in the catch-all pattern: _ 是一种特殊模式，它与任何值相匹配，没有绑定到那个值。 这告诉Rust 我们不会使用该值，因此Rust 不会就一个未使用的变量向我们发出警告。

让我们改变游戏规则：现在，如果你滚动了3或7个以外的其他东西，你必须重新滚动。 我们不再需要使用包罗万象的值，这样我们就可以更改我们的代码来使用_ 而不是变量名为other

fn main() {
    let dice_roll = 9;
    match dice_roll {
        3 => add_fancy_hat(),
        7 => remove_fancy_hat(),
        _ => reroll(),
    }

    fn add_fancy_hat() {}
    fn remove_fancy_hat() {}
    fn reroll() {}
}

这个例子也符合详尽无遗的要求，因为我们明确无视最后一支武器中的所有其他价值；我们没有忘记任何东西。

末尾。 我们将再次更改游戏规则，以便如果你滚动3或7个以外的任何其他东西，你的轮转不会发生任何其他事情。 我们可以通过使用单位值来表达这一点(我们在“Tuple Type”<中提到的空管类型) ！ - 忽略 –> 节作为带有“_“ 臂的代码：

fn main() {
    let dice_roll = 9;
    match dice_roll {
        3 => add_fancy_hat(),
        7 => remove_fancy_hat(),
        _ => (),
    }

    fn add_fancy_hat() {}
    fn remove_fancy_hat() {}
}

这里我们明确告诉你, 我们不会在早些时候的手臂中使用不匹配模式的任何其他值。 我们不想在此案中运行任何代码。
