The Rust Programming Language

不安全的Rust

到目前为止，我们所讨论的所有代码都遵循了Rust的内存安全保证，这些保证在编译时就会得到落实。不过，Rust内部还隐藏着另一种语言，它并不强制执行这些内存安全保证。这种语言被称为“不安全Rust”。虽然它的运作方式与普通Rust相同，但它为我们提供了额外的功能。

Unsafe Rust的存在是因为，从本质上讲，静态分析是一种保守的方法。当编译器试图判断代码是否遵守了相关规范时，与其接受一些无效的代码，不如拒绝一些合法的代码。虽然代码本身可能没有问题，但如果Rust编译器没有足够的信息来做出判断，它就会拒绝该代码。在这种情况下，你可以使用unsafe代码来告诉编译器：“相信我，我知道自己在做什么。”不过需要注意的是，使用unsafe代码需要你自己承担风险：如果你错误地使用了这种代码，可能会因为内存安全问题而出现问题，比如空指针解引用。

Rust之所以有“不安全”的版本，另一个原因是底层计算机硬件本身具有不安全性。如果Rust不允许执行不安全操作，那么许多任务就无法完成。Rust需要允许开发者进行低级系统编程，比如直接与操作系统交互，甚至编写自己的操作系统。进行低级系统编程正是该语言的目标之一。让我们来探讨一下如何使用Rust的“不安全”版本来完成这些任务。

行使不安全的超能力

要切换到不安全的Rust环境，可以使用unsafe这个关键字，然后开始一个新的代码块，其中包含了不安全的代码。在不安全的Rust环境中，你可以执行一些在安全Rust中无法进行的操作，这些操作我们称之为“不安全的超能力”。这些超能力包括：

  1. 解引用原始指针。
  2. 调用不安全的函数或方法。
  3. 访问或修改可变的静态变量。
  4. 实现不安全的特性。
  5. 访问 unions 的字段。

需要明白的是，unsafe并不会关闭借用检查器，也不会禁用Rust的其他安全检查机制：如果你在unsafe代码中使用了引用，这些引用仍然会被进行检查。unsafe这个关键字只是让你能够访问这五个特性，而这些特性不会由编译器进行内存安全性的检查。尽管如此，你在unsafe代码块内仍然可以获得一定程度的安全性保障。

此外，unsafe并不意味着该代码块中的内容一定具有危险性，或者一定会存在内存安全方面的问题。其目的是让程序员能够确保位于unsafe代码块中的代码能够以合法的方式访问内存。

人们都会犯错，错误是难免的，但是通过要求这五种不安全操作必须位于带有 unsafe 注释的块中，你就可以确保与内存安全相关的任何错误都发生在 unsafe 块内。尽量保持 unsafe 块的小规模；这样在排查内存漏洞时你会感到庆幸。

为了尽可能隔离不安全的代码，最好将这些代码封装在一个安全的抽象层中，并提供安全的API。我们将在后面的章节中讨论如何设计不安全的函数和方法。标准库中的某些部分就是通过将不安全的代码进行安全化处理来实现的。将不安全的代码封装在安全的抽象层中，可以防止unsafe被泄露到那些你可能想要使用unsafe实现的功能的地方，因为使用安全的抽象层本身就是一种安全的做法。

让我们依次来看看这五个“不安全超级功能”。同时，我们还会了解一下一些能够为不安全代码提供安全接口的抽象概念。

解引用原始指针

在第4章的“悬空引用”部分中，我们提到编译器会确保引用始终有效。不安全的Rust语言中有两种新类型，称为“原始指针”，它们与引用类似。与引用一样，原始指针可以是不可变的，也可以是可变的，并且分别被表示为*const T和*mut T。星号并不是解引用运算符；它是类型名称的一部分。在原始指针的上下文中指针，_不可变_意味着在解引用之后，该指针不能被直接赋值给另一个变量。

与引用和智能指针不同，原始指针：

  • 允许使用不可变指针和可变指针或多个可变指针来忽略借用规则，从而指向同一位置
  • 不保证会指向有效的内存地址
  • 允许为空值
  • 不实现任何自动清理机制

通过选择不让Rust执行这些保证，你可以放弃有保障的安全性，以换取更高的性能，或者能够与其他语言或硬件进行交互，而Rust的保证在这些情况下并不适用。

调用不安全的函数或方法

在不安全代码块中，你可以执行的第二种操作是调用unsafe函数。这些unsafe函数和方法的样子与普通函数和方法完全相同，但它们在定义内容的前面多了一个unsafe。这里的unsafe关键字表示，在调用这些函数时，我们必须满足一些要求，因为Rust无法保证我们满足了这些要求。通过在不安全代码块内调用unsafe函数，我们可以实现特定的功能。在unsafe块中，我们表示已经阅读了该函数的文档，并且我们愿意承担维护该函数契约的责任。

这里有一个名为dangerous的不安全函数，其主体中没有任何操作：

fn main() {
    unsafe fn dangerous() {}

    unsafe {
        dangerous();
    }
}

我们必须在一个单独的unsafe块中调用dangerous函数。如果我们试图在没有unsafe块的情况下调用dangerous，将会出现错误。

在unsafe函数的主体中执行不安全的操作时，仍然需要使用unsafe块，就像在普通函数中一样。如果你忘记了这一点，编译器会发出警告。这样做有助于我们将unsafe块保持尽可能小，因为并非整个函数体内都需要执行不安全的操作。

使用extern函数调用外部代码

有时候，你的Rust代码可能需要与用其他语言编写的代码进行交互。为此，Rust提供了extern这个关键字，它可以帮助创建和使用_外部函数接口_(FFI)_，这是一种让一种编程语言定义函数，并让另一种不同的（外部）编程语言调用这些函数的方式。

清单20-8展示了如何与C标准库中的abs函数进行集成。在extern块内声明的函数通常不适合在Rust代码中调用，因此extern块也必须被标记为unsafe。原因在于其他语言并不强制执行Rust的规则和保证，而Rust无法对这些规则进行验证，因此确保安全性的责任落在程序员身上。

在unsafe extern "C"块中，我们列出了想要调用的其他语言中的外部函数的名称和签名。"C"部分定义了该外部函数所使用的应用程序二进制接口(ABI)：ABI决定了在汇编级别如何调用该函数。"C" ABI是最常见的类型，遵循C编程语言中的ABI规范。关于Rust支持的所有ABI的信息可以在Rust参考手册中找到。

在 unsafe extern 块中声明的每个项都默认是不安全的。不过，有些外部库函数是可以安全调用的。例如，C语言标准库中的 abs 函数没有任何内存安全方面的考虑，我们知道它可以与任何 i32 一起被调用。在这种情况下，我们可以使用 safe 关键字来表明这个特定的函数是可以安全调用的，即使它位于不安全的代码区域内。一个unsafe extern块。一旦我们进行了这样的修改，调用它就不再需要unsafe块了，如清单20-9所示。

将某个函数标记为 safe 并不能使其本身变得安全！这实际上是一种向Rust做出的承诺，即该函数是安全的。确保这一承诺得到履行仍然属于你的责任！

使用其他语言调用Rust函数

我们还可以使用extern来创建一个接口，使得其他语言能够调用Rust函数。无需创建完整的extern块，我们可以在fn关键字之前添加extern关键字，并指定要使用的ABI。同时，我们还需要添加#[unsafe(no_mangle)]注释，以告知Rust编译器不要修改该函数的名称。_修改_当编译器将我们给函数的名称改为另一个名称时，这个名称会包含更多信息，这些信息会被编译过程的其他部分使用，但可读性较差。每种编程语言的编译器对名称的处理方式都略有不同。因此，为了让Rust函数能够被其他语言命名，我们必须禁用Rust编译器的名称处理功能。这样做是不安全的，因为不同库之间可能会出现名称冲突。进行混淆处理，因此我们的责任是确保所选择的名称在导出过程中不会受到混淆影响，保持安全性。

在下面的示例中，我们使得在C代码中对call_from_c函数的访问成为可能，这一过程包括将其编译成共享库，并从C代码中进行链接。

#[unsafe(no_mangle)]
pub extern "C" fn call_from_c() {
    println!("Just called a Rust function from C!");
}

这种使用extern的方式要求unsafe仅存在于属性中，而不出现在extern块中。

访问或修改可变静态变量

在本书中，我们尚未讨论全局变量。虽然Rust支持全局变量，但在Rust的所有权规则下，使用全局变量可能会带来问题。如果两个线程同时访问同一个可变的全局变量，可能会导致数据竞争。

在Rust中，全局变量被称为_静态_变量。清单20-10展示了一个静态变量的声明和使用示例，其中字符串切片被用作该变量的值。

静态变量与常量类似，我们在第3章的“声明常量”部分中讨论过相关内容。静态变量的名称按照惯例被放在SCREAMING_SNAKE_CASE中。静态变量只能存储'static生命周期内的引用，这意味着Rust编译器可以自行确定其生命周期，我们无需显式进行注释说明。访问不可变的静态变量是安全的。

常数与不可变的静态变量之间的一个微妙区别在于，静态变量中的值在内存中有固定的地址。使用这些值时，总是可以访问相同的数据。而常数则可以在使用时随时复制其数据。另一个区别是，静态变量可以是可变的。访问和修改可变的静态变量是不安全的。清单20-11展示了如何声明、访问和修改一个名为COUNTER的可变静态变量。

与常规变量一样，我们使用mut关键字来指定变量的可变性。任何从COUNTER读取或写入数据的代码都必须位于unsafe块内。正如我们所预期的那样，清单20-11中的代码能够编译并打印出COUNTER: 3，因为它是在单线程环境下运行的。如果多个线程访问COUNTER，可能会导致数据竞争，因此这属于未定义的行为。因此，我们需要采取适当的措施来确保线程安全。将整个函数标记为 unsafe，并详细说明安全限制，以便调用该函数的任何人都能了解允许和禁止做的事情。

每当我们编写不安全的函数时，通常会使用如下形式的注释来说明：以SAFETY开头，并解释调用者需要做什么才能安全地调用该函数。同样地，每当我们进行不安全的操作时，也会使用类似的形式的注释来说明如何遵守安全规则。

此外，编译器默认会拒绝任何通过编译器的检查来创建对可变静态变量的引用的尝试。您必须明确选择放弃这些保护措施，方法是添加#[allow(static_mut_refs)]注解，或者通过一些原始借用运算符创建的原始指针来访问可变静态变量。这包括那些以不可见方式创建引用的情况，比如在代码中使用这样的引用时。在这段代码清单中使用了println!。要求通过原始指针来创建静态可变变量，这有助于使使用这些变量的安全要求更加明确。

由于数据是可变的且可以全局访问，因此很难确保不会出现数据竞争的情况。这就是为什么Rust认为可变的静态变量是不安全的。在可能的情况下，最好使用我们在第16章中讨论的并发技术以及线程安全的智能指针，这样编译器就能检查来自不同线程的数据访问是否安全进行。

实现不安全特性

我们可以使用 unsafe 来实现一个不安全的特性。当一个特性的至少其中一个方法包含编译器无法验证的不变性时，该特性就被视为不安全的。我们通过在 trait 之前添加 unsafe 关键字，并将特性的实现标记为 unsafe，来声明该特性是 unsafe 的，如清单 20-12 所示。

通过使用unsafe impl，我们承诺会遵守那些编译器无法验证的不变量。

作为一个例子，回顾我们在“与Send和Sync的可扩展同义。]中讨论的 Send 和 Sync 标记特性！ - 忽略 –> 第16章的章节：如果我们的类型完全由实现Send和Sync的其他类型组成，编译器会自动实现这些特性。 如果我们实现了一个类型包含不执行 Send 或 Sync 的类型， 比如原始指针，我们想要将这种类型标记为 Send 或 Sync，我们必须使用 `不安全’。 不能验证我们的类型是否支持保证它可以安全地通过线程发送或从多个线程访问； 因此，我们需要手工进行这些检查，并以“不安全”表示。

访问联合字段

最后一个适用于unsafe的操法是访问联合体的字段。
“联合体”类似于struct，但在特定情况下，一次只能使用一个已声明的字段。联合体主要用于与C代码中的联合体进行交互。访问联合体的字段是不安全的，因为Rust无法保证当前存储在联合体中的数据的类型。您可以在Rust参考手册中了解更多关于联合体的信息。

使用Miri检查不安全代码

在编写不安全的代码时，你可能需要检查自己所写的代码是否真正安全且正确。实现这一目标的最佳方法之一是使用Miri，这是Rust官方提供的一个用于检测未定义行为的工具。虽然borrow checker是一个在编译时生效的静态工具，但Miri则是一个在运行时生效的动态工具。它通过运行你的程序或其测试套件来检测你的代码，并识别出你违反了Rust规范所规定的规则。

使用Miri需要安装最新版本的Rust（我们在附录G：Rust的制造过程与“Nightly Rust”中有更多介绍）。您可以通过运行rustup +nightly component add miri来安装最新版本的Rust以及Miri工具。这一操作并不会改变项目所使用的Rust版本；它只是将Miri工具添加到您的系统中，以便您可以在需要时使用它。您可以通过输入cargo +nightly miri run或cargo +nightly miri test来运行Miri工具。

Miri并不能捕捉到你在编写不安全代码时可能犯的所有错误。Miri是一种动态分析工具，因此它只能发现实际运行时的代码问题。这意味着你需要结合良好的测试技术来使用它，以提高对编写的不安全代码的信心。此外，Miri并不能涵盖代码中所有可能出现的问题。

换句话说：如果Miri确实发现了问题，那么显然存在错误；但仅仅因为Miri没有发现错误，并不意味着就没有问题。不过，它确实有可能发现很多问题。试着在本章中其他不安全的代码示例上运行一下，看看它会显示什么结果！

正确使用不安全代码

使用 unsafe 来使用刚才提到的五种超能力之一，这本身并没有错，甚至也不被提倡。但是，要确保 unsafe 代码的正确性则更为复杂，因为编译器无法完全保证内存安全。当你有理由使用 unsafe 时，你可以这样做。而使用明确的 unsafe 注释，则有助于更容易地追踪问题发生的根源。编写不安全的代码时，可以使用Miri来帮助你更放心地编写代码，确保你所写的代码符合Rust的规范。

如果您想更深入地了解如何有效地使用不安全的Rust，请阅读Rust的官方指南《Rust’s official guide for unsafe》，以及《The Rustonomicon》(https://doc.rust-lang.org/nomicon/)。
