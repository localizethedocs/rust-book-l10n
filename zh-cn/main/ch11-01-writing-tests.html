The Rust Programming Language

如何编写测试

Tests 是 Rust 函数来验证非测试代码是否以预期方式运行。 各种测试功能通常执行这三种操作：

  • 设置任何需要的数据或状态。
  • 运行您想要测试的代码。
  • 验证结果是否符合预期。

让我们来看看Rust为编写执行这些操作的测试而提供的一些特性，其中包括test属性、几个宏，以及should_panic属性。

测试函数的结构设计

在Rust中，测试最简单的形式就是一个带有 test 属性的函数。属性是关于Rust代码的元数据；例如，在第5章中我们使用的 derive 属性用于结构体。要将一个函数转换为测试函数，需要在 fn 之前的行添加 #[test]。当你使用 cargo test 命令运行测试时，Rust会构建一个测试运行程序，该程序会执行这些带有属性的函数，并报告每个测试函数是否通过或失败。

每当我们使用 Cargo 创建一个新的库项目时，系统会自动生成一个包含测试函数的测试模块。这个模块为你提供了编写测试的模板，这样你就不需要每次开始新项目时都去查找具体的结构和语法了。你可以根据需要添加任意数量的额外测试函数和测试模块！

我们将通过实验模板 test 来探索测试的工作原理。在实际测试任何代码之前，我们先进行这样的实验。然后，我们会编写一些实际场景的测试，这些测试会调用我们编写的一些代码，并验证其行为是否正确。

使用 assert! 检查结果

标准库提供的assert!宏在需要确保某个测试条件满足true时非常有用。我们给assert!宏一个可以评估为布尔值的参数。如果该值为true，则不会发生任何事情，测试通过。如果值为false，则assert!宏会调用panic!来使测试失败。使用assert!宏可以帮助我们检查代码是否按照我们的预期运行。

通过assert_eq!和assert_ne!测试平等

验证功能的常见方法是测试测试测试代码结果与您期望代码返回的值之间的平等。 你可以使用 “sert!” 宏来做到这一点，然后使用 “=” 操作员传递一个表达式。 然而，这是一种常见的检验标准，以至于标准库提供了一对宏——assert_eq!和assert_ne!——以便更方便地进行这种检验。 这些宏观分别比较了关于平等或不平等的两个论点。 如果断言失败，他们也会打印两个数值，这使我们更容易查看 why 测试失败；反之，断言！ 宏只表示它获得了==表达式false值，而没有打印导致false`值的值。

如果我们给它的两个值不平等，如果它们是平等的，将会失败，这个宏将会传递。 当我们不知道_will_是什么值时，这个宏最有用，但我们知道_shouldn肯定是什么值。 例如，如果我们正在测试一个能保证以某种方式更改其输入的函数， 但更改输入的方式取决于我们运行测试的那个星期的那天。 最好的说法可能是，该功能的输出与投入不等。

正在检查带有“should_panic“ 的Panics

除了检查返回值外，还要检查我们的代码是否按预期处理错误条件。例如，考虑我们在第9章，第9-13条目中创建的“猜测”类型。其他使用“猜”的代码依赖于保证“猜测”实例只包含1到100之间的值。我们可以写一个测试，确保尝试创建值超出该范围的“猜测”实例时会发生恐慌。

我们通过将属性 ‘should_panic’ 添加到我们的测试函数来做到这一点。 如果函数中的代码在函数恐慌中，测试会通过；如果函数内的代码不会惊慌，测试会失败。

使用 “should_panic” 的测试可能不准确。 “should_panic”测试将会通过，即使测试恐慌与我们期望的原因不同。 要使should_panic 测试更加精确，我们可以在 should_panic 属性中添加一个可选的 expected 参数。 测试方式将确保故障消息包含所提供的文本。 例如， 考虑列表11-9中Guess修改后的代码，其中new函数会因值太小还是太大而产生不同的信息而产生恐慌。

在测试中使用 结果<T, E>

我们迄今为止的所有测试都在失败时恐慌。 我们也可以使用 “结果<T, E>” 写测试！ 这是上架11-1的测试，重写后使用 结果<T, E>返回一个 Err 而不是恐慌：

pub fn add(left: u64, right: u64) -> u64 {
    left + right
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn it_works() -> Result<(), String> {
        let result = add(2, 2);

        if result == 4 {
            Ok(())
        } else {
            Err(String::from(“二加二不等于四”))
        }
    }
}

it_works函数现在有Result<(), String>返回类型。 在函数正文中，而不是调用 assert_eq! macro, 我们在测试通过时返回 Ok(), 当测试失败时返回Err, 和 String` 。

写入测试，让他们返回一个 结果<T, E> ，使您能够在测试体内使用问号标记操作员。 它可以成为写入测试的方便方式，如果它们内部的任何操作返回一个 Err 变量就会失败。

您不能在使用 结果<T, E>的测试上使用#[should_panic]注释。 要断言操作返回一个 Err 变量, _don’_使用在 结果<T, E> 上的问题标记运算符, 而是使用 assert!(value.is_err()) 。
